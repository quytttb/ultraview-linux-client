## KDE global menu — 2026-10-19 (0.2.1)

- Desktops that ask for an application menu (KDE Plasma's *Global Menu* panel
  widget, a menu button in a window decoration, …) now get the actions this
  client offers there. `src/platform/GlobalMenu.{h,cpp}` describes the menu and
  hands the bar to the main window; Qt's Unix platform theme renders it as a
  `com.canonical.dbusmenu` object and announces it to the window manager (an X11
  window property, or the `org_kde_kwin_appmenu` Wayland protocol). The QML
  toolbar is unchanged and nothing is drawn inside the window for this feature.
- The QPA menu API is private Qt API, so the feature is compiled only when the
  distribution ships the private QtGui headers and Qt is ≥6.9
  (`qt6-base-private-dev` here; CMake defines `ULTRAVIEW_HAVE_GLOBAL_MENU`).
  Without them the client builds and runs unchanged without a global menu, and
  `GlobalMenu` still exists because QML binds its `statisticsVisible` property.
  `dpkg-shlibdeps` then records the runtime requirement
  `qt6-base-private-abi (= 6.10.2)`, which the installed Qt provides — the same
  pattern Plasma's own packages use.
- Live check on this machine (Plasma 6.6.6, Wayland, session bus with kded6's
  `com.canonical.AppMenu.Registrar`): `WAYLAND_DEBUG=1` shows
  `org_kde_kwin_appmenu_manager#…create(…, wl_surface#…)` followed by
  `org_kde_kwin_appmenu#…set_address(":1.171", "/MenuBar/1")`, i.e. the window was
  announced to KWin. `com.canonical.dbusmenu.GetLayout` on that object returned the
  expected tree, with labels, freedesktop icon names, `toggle-type`/`toggle-state`
  and the separator carried as properties: Session (Connect and Disconnect

  actions as the toolbar, not a copy.

## Relay certificate identity — 2026-10-20 (0.2.4)

- The first real interface attempt (partner `118925568`, 2026-10-19 23:52 local)
  reached the service and failed with *"TLS certificate verification failed: The
  host name did not match any of the valid hosts for this certificate"*. The
  registration endpoint itself verifies:
  `openssl s_client -connect functions3.ultraviewer.net:443 -servername
  functions3.ultraviewer.net -verify_hostname functions3.ultraviewer.net` reports
  `subject=CN=*.ultraviewer.net`, issuer
  `Sectigo Public Server Authentication CA DV R36` and
  `Verify return code: 0 (ok)`.
- Diagnosis (from the pinned reference, not guesswork): route field 14
  (`tcp_server_hostname`) is passed only as the HTTP `Host:` header of the relay
  preface — `SessionTransport.connect(self.route.tcp_server_ip, 443,
  http_hostname=self.route.tcp_server_hostname)` — while both channels wrap TLS
  with the same `TLS_TARGET_HOST` literal. The native client had been verifying
  the relay against the route field, an identity the vendor certificate never
  carries. This fixes a recovery assumption; it does not relax verification:
  chain and host-name checks stay on.
- 0.2.4 authenticates the relay with the service certificate name (the
  registration certificate name: `registrationPeerName`, else the registration
  host). A new **Relay certificate name** setting (`endpoints/relayPeerName`)
  overrides it explicitly; an explicit relay connect-host override still
  authenticates that host. `route.tcpServerHostname` is used only as the HTTP
  `Host:` header.
- TLS failures now report the expected name and the peer certificate's subject
  alternative names, so a remaining mismatch is diagnosable from the status bar
  without packet captures.
- Offline integration replaces the previous (incorrect) expectation in
  `tst_session`: `relayAuthenticatesTheRegistrationCertificateName` advertises
  `wrong-relay.invalid` in the route, verifies the relay, and asserts the preface
  sends `Host: wrong-relay.invalid`;
  `relayCertificateNameOverrideIsRefusedWhenItDoesNotMatch` proves an explicit
  mismatching certificate name is refused before `login:`. 14/14 CTest targets
  pass; the installed 0.2.4 binary passes `--self-test`, and the live probe
  (`--connect-attempt 999999999`) still reads the reference's status-11 refusal,
  so the registration path is unchanged.
- `ultraview_0.2.4_amd64.deb` (11,008,492 bytes,
  `a542091047d0fc88fa5ea04ce925a8d7f4fa0a02cc8c263a1771b677ed152434`) declares
  the same dependencies as 0.2.3 (including `libsecret-1-0`), was extracted and
  installed (`0.2.4: install ok installed`), and the extracted and installed
  binaries pass `--self-test`.
- The live retry with the partner password is **pending**; if the vendor relay
  does not present the wildcard certificate, the reported SANs will record what it
  presents and this section will be updated.

## Full screen, clearer settings and Wayland shortcut routing — 2026-10-20 (0.2.8)

- A full-screen exit had restored `Windowed`, making the partner desktop appear
  smaller. Opening the viewer now maximizes the window; full screen uses the
  explicit `QWindow::showFullScreen()` compositor request and restores the prior
  maximized/windowed state with `showMaximized()`/`showNormal()`. The in-app
  header and footer are hidden. The viewer toolbar no longer occupies fixed screen
  height: it is a floating overlay revealed by moving the pointer to the top edge
  and hides after 1.8 seconds away from it. Its blank area consumes pointer events
  so revealing it cannot click the partner desktop.
- While connected with remote input enabled, the app no longer reserves Ctrl+Q,
  F11 or Esc: the input mapper sends them to Windows (as it already does
  `Meta`/`Super_L`/`Super_R` to VK `0x5B`/`0x5B`/`0x5C`). The local toolbar is the
  deliberate full-screen/Disconnect escape route. The global-menu Quit
  accelerator is also removed during active remote input and restored afterwards.
- The local desktop also used to see Super/Meta because that key was captured by
  the compositor before Qt received it. On this KDE Wayland session, `wayland-info`
  reports `zwp_keyboard_shortcuts_inhibit_manager_v1` and a direct Qt/Wayland
  probe bound it and received its `active` callback from KWin 6.6.6. The app now
  requests that standard protocol only while the window is active, remote input
  is enabled and a session is connected; it releases it otherwise. Thus KWin
  forwards desktop shortcuts to the viewer for relay to the partner. The feature

  dev package builds require both. Desktops without this protocol cannot promise

## Host (sender) mode and UI — 2026-10-29

- Commit `0a95b08` added the host core: `HostProfile` (private 32-hex identity and
  8-digit password at `<AppConfig>/host-profile.json`), `HostProtocol`
  (28-field registration, relay negotiation, 23-field viewer login, RGB555/zstd
  frames, control permission), `HostSession` (login proof, 5-failure/5-minute
  throttle, 45-second approval, frame pacing, input gating), `HostManager`
  (worker-thread registration/relay orchestration), `HostBackend`,
  `InputMapping` and `WaylandPortal` (ScreenCast + RemoteDesktop over
  QtDBus/PipeWire).
- `HostViewModel`, the Host page and the approval dialog wire that core into the
  application. The header switches between Control and Host; opening Host only
  loads the identity, and only **Start hosting** starts registration and the
  portal. The approval dialog requires **Allow control**, **View only** or
  **Refuse**, and Escape refuses. Hosted sessions can switch control/view-only
  through command 49. The host page states that chat, clipboard, transfer and
  audio are not implemented.
- `tst_host` now has 19 protocol/session/profile/layout/input-mapping tests
  covering registration terms, relay parsing, login proofs, throttle, frame
  encoding and pacing, approval timeout, host layout scaling and pointer/key
  mapping. It also creates and reloads a host profile at an explicit path,
  checks the stable identity/password, the 0700 directory and 0600 file modes,
  and refuses malformed JSON. The full suite is **19/19** in RelWithDebInfo. The
  offscreen Host page was reviewed with `--screenshot-view host`; the layout fits
  1024×720 and the empty identity/backend diagnostics render correctly.
- Packaging/CI builds request `-DULTRAVIEW_REQUIRE_WAYLAND_HOST=ON`; the package
  recommends `xdg-desktop-portal`, a portal backend and PipeWire. Runtime host
  dependencies are otherwise the same PipeWire client library as audio.
- Live capture was validated on this KDE Wayland session (Plasma,
  `xdg-desktop-portal` 1.21.1, `xdg-desktop-portal-kde` 6.6.6, PipeWire 1.6.2)
  with a temporary probe outside the repository. Two live-only defects were found
  and fixed: KDE rejects persistence for remote-desktop sessions, so
  `persist_mode`/`restore_token` were removed; and `Start` must be sent to
  `RemoteDesktop` (not `ScreenCast`) or the frontend never records the stream
  list and `OpenPipeWireRemote` fails with "No streams available". The PipeWire
  event table is now owned by the stream state instead of a stack local, fixing a
  crash in the PipeWire data thread. The probe returned one 1920×1080 display,
  a 1920×1080 layout and 4,147,200 RGB555 bytes with 2,073,055 non-black pixels.
- Not validated: a real Windows UltraViewer viewer controlling this host, portal
  pointer/keyboard injection actually moving the local desktop, the approval
  dialog against a real viewer, and stop/cleanup on a live session. No host
  password or profile is written by the test suite or the package.
